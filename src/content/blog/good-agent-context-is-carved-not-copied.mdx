I’ve been experimenting with different combinations of AI models and agents for my software development workflows, which is a nice way of saying I've spent a lot of evenings arguing with robots about whether we actually needed a new abstraction layer.

For me this journey started with a lot of browser-based chat. Optimize that prompt, paste in the error message, receive the wisdom. That worked for smaller changes but as projects scaled that "wisdom" started drifting somewhere between helpful and hallucinated.

Then I worked with repo-aware coding agents like Codex, OpenCode, and Pi. These tools stay closer to the actual project — they inspect real files, check real state, and put a lot less air between what you say and what you code.

That was a good start. The results were still unpredictable, just unpredictable with better posture.

Ask one agent for a small, focused change, and it makes said change. Ask another agent the same thing and it gives you that change plus a few unrelated file rewrites, all with the quiet confidence of someone giving you a "you're welcome" nod. Same instruction, wildly different dude showing up to work.

The problem wasn't that one response was right and another was wrong. It was that the same request could produce several plausible interpretations, each built on assumptions I hadn't realized I'd left open. Inconsistency was the symptom. Ambiguity was the actual problem.

As an engineer I'd gotten used to prescriptive configuration doing the heavy lifting. A formatter config or build script has explicit rules. Define values correctly and the system does exactly what you told it to, every time, without opinions.

I unintentionally brought that same expectation to AI. Better instructions, I assumed, would produce more consistent, predictable results. Instead, the same prompt could behave differently depending on the model, the agent, or which "thinking mode" it woke up with that morning. The instructions still mattered, but they just weren't rules anymore. They were more like suggestions with a mood.

I had come to realize what I was doing. With AI I wasn't configuring a deterministic system. I was shaping the context that a probabilistic one used to make a judgment call. Judgment calls, it turns out, need a very different kind of setup than a config file ever did.

So I did what any reasonable engineer does when facing an ambiguous problem: I went looking for someone else's homework. Except this time I wasn't hunting for better prompts, I'd figured out that was a dead end. I was after something more durable: context that gives an agent a stable place to stand.

I pored over Github repositories, social feeds, and technical blogs and…

**"New achievement! You have created an AGENTS.md file!"**

Yes, I started writing agent files and that did take some practice. I needed to author a clear role for the agent(s) with a succinct, definitive project ruleset. There could be no duplication or contradiction. And yes, it would help to be a little psychic with those assumptions. For that last part, I leaned on the agents themselves for copy-edit assists, which is its own small joke: using the tool to fix the document meant to constrain the tool.

Suddenly the ground stopped shaking. Not perfectly. Agents still had opinions, still occasionally wandered, but the opinions started to rhyme with one another. Two different tools, given the same sheet music, began playing the same music.

From here I kept carving. I started using the Pi agentic harness, whose deliberately tiny system prompt gave me a clean slate to build context onto, instead of one already crowded with someone else's assumptions. I also added agent skill files, but not off the shelf. I opinionated each to best fit my specific use cases.

I also began linking the `AGENTS.md` file to a very careful combination of agent-relevant documentation. My decision to add a doc usually traced back to one specific failure mode I wanted to hone or correct for the agent. Over time I'd decide whether to keep it, trim it, or yank it back out entirely. And once I had more than one agent in the loop, a planner here, an implementer there, documentation for a single agent's role started needing to become documentation for a whole small cast of them. What I landed on was less a stack of documentation and more a small, deliberate set of answers to specific questions. Here's roughly where I ended up:

| Document Type | Purpose |
|---|---|
| Architecture Decision Record (ADR) | Records a significant technical decision, its context, alternatives considered, and consequences |
| Technical Design Document | Explains how a system or feature is built and why it's shaped that way |
| Spec | Defines what a feature or change must do, including constraints and acceptance criteria |
| Runbook | Step-by-step instructions for a specific operational task, like deploying or rolling back |
| Roles Documentation | Defines who or what is responsible for a given task or decision, especially when multiple agents are involved |
| Glossary | Domain vocabulary and terms that mean something more specific here than they do generically |

None of these are exotic. Most teams have some version of a few, half-finished, in a wiki nobody opens on purpose. The difference wasn't inventing new documentation. It was linking the right pieces to the agent deliberately, instead of leaving them to be found by accident or not at all.

I'm still testing combinations, honestly, and I've gone back and forth on whether certain docs earn their place or just add weight. Link too little and the agent's back to guessing. Link too much and you've built a context window with a hoarding problem: technically complete but practically unreadable and expensively slow. The fix was treating this like any other performance budget. Not everything loads up front. An index can point toward a runbook without pulling the whole thing into context until it's actually needed. The rule I keep coming back to: keep what's cheap to re-verify and expensive to guess wrong; link what's expensive to hold and rare to need.

This reframe also got me thinking in terms I already knew. I'd spent decades optimizing User Experience, UX. Somewhere in this process I realized I'd also been prioritizing Developer Experience, DX, in shaping how a team writes and finds documentation in the first place. Now there was a third audience I hadn't budgeted for. The agent itself would read the same files and build the same understanding, with none of the forgiving context a human brings by default. Call it Agent Experience, AX. It deserved its own design consideration, not a leftover corner of the other two.

That idea isn't just a hunch of mine. Google Cloud published the Open Knowledge Format specification in June 2026, an attempt to standardize this exact shape of problem: a plain directory of markdown files, authored by people or agents, read by either, with no translation layer between "docs for us" and "docs for it." It's early, and Google calls it a starting point rather than a finished standard, but it's a signal I'm glad to see. I wasn't the only one thinking about context as something designed for more than one kind of reader.

I'm certain this context engineering will keep changing. The line between UX, DX, and AX will get redrawn more than once, but deciding what an agent actually needs to know won't go out of style. So I'll keep experimenting, one overconfident agent and one hastily written rule at a time.
